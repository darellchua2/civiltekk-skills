## Decision: laya-guard runs ONNX in a Node sidecar — opencode v2's plugin runtime is embedded Bun, not Node

**Context** (#671, 2026-10-11): The laya-guard brief assumed an in-process ONNX gate on "Node 20+" and that opencode v2 runs plugins under Node. Both assumptions failed verification. Evidence chain, all primary-source: (1) the installed binary (`@opencode/cli@2.0.26`, an ELF under nvm Node 24) contains `Bun v1.4.2` and 2,639 `/$bunfs/root/chunk-*.js` strings — the virtual-FS signature of `bun build --compile`; system Node never executes the app (npm is just the delivery channel; `postinstall.mjs` is the only code Node runs). (2) Tag `v2.0.26` (commit `9b4ec57`) pins `"packageManager": "bun@1.4.2"`, `bun test`, and a Bun-compile release script. (3) A Node distribution DOES exist — `script/build-node.ts` builds a Node 26.4 SEA (`opencode2-node`) — but it is not what npm ships. (4) The string `node/v26.3.0` inside the binary is Bun's Node-compat version report, not an embedded Node.
**Pattern**: In-process native modules (onnxruntime-node) would load under opencode's embedded Bun — N-API-under-Bun has open breakage reports (#3574 bus error, #18079) and the runtime is not user-selectable. The laya-guard design therefore keeps the plugin file zero-dependency (house rule, vibeguard-v2 pattern) and spawns a **Node >= 24 sidecar** (`~/.cache/laya-guard/sidecar.mjs`, JSONL over stdio, deps + model provisioned by setup.sh). The sidecar exits on stdin close — lifecycle-bound to opencode without a daemon. Local-plugin npm dependencies have NO documented v2 mechanism (the config-dir `package.json` + `bun install` text is V1-docs only) — another reason deps live in the sidecar, not the plugin.
**Rationale**: `bun install`/`$`-shell statements and hook shapes sourced from `https://opencode.ai/docs/...` describe **V1**; v2 truth lives at `/v2/docs/...` (plugin API: `Plugin.define`/`setup(ctx)`, `ctx.permission.hook("evaluate")` with mutable `effect`, `ctx.tool.transform` for custom tools, `permission.asked` observe-only). When a runtime fact gates an architecture decision, verify the installed binary (`strings`/`file`) and the exact release tag — docs and npm placement both mislead.
**Alternatives Considered**: In-process under embedded Bun (rejected: unverifiable native-module compat against a binary the user cannot rebuild; the two Bun issues are version/platform-specific and opencode pins its own Bun). Publishing an npm plugin package to get the managed dependency path (rejected: heavy for one consumer; sidecar needs no plugin-host mechanism at all). Node SEA channel (`opencode2-node`) as the target (rejected: not the shipped default; user runs the Bun build).
**Trade-offs**: Pro — officially supported inference runtime (onnxruntime-node: Node 16+, rec 20+), deterministic sidecar runtime independent of opencode releases, zero-dep plugin file, model warmed once per session (~140 ms per 3-question batch after load). Con — one extra process (~2 GB RAM with the fp32 model) and a stdio protocol to maintain; Node >= 24 required on PATH.
**Verified live** (#671): warm pull + `systemOne` through the provisioned sidecar on Node 24.21.0 — calibrated outputs (destructive p=0.94 on `rm -rf node_modules`; exfiltration p=0.91 on `curl -d @.env`), drain-then-exit clean.
